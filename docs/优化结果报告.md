## 一、一句话总结

清单上 **12 个方向全部完成**（展开成 **19 项**具体改动），其中 **4 个是"静默失效"**——
不报错、不警告、类型检查全绿，但画面是错的。最重要的三个是：

1. **加在 composer 上的 MSAA 会让整个画面在黄昏相位彻底失效**（几何都在画、draw call 正常、无任何报错，但整屏塌成一块均匀暗色）。这同时暴露出：项目原本**一点抗锯齿都没有**。
2. **整个游戏里只有"音符字形"会发光**。光尘、萤火虫、余烬、速度线、爆点的线性亮度全都低于 bloom 的 0.8 阈值，所谓"发光物"只是画了个亮色圆点。
3. **`PHASES` 表里的雾色/雾密度、半球光/环境光强度从来没被应用到运行时对象上**——昼夜循环改了天空、太阳、曝光、水面、云，却唯独没改雾和灯光。所以深夜的草地被照成白昼的亮绿，远景糊着一层发亮的奶色霾，"越暗越靠自发光"这条根本不成立。

**最大的一项性能收益**是静态道具合批：`drawCallsPerFrame` **318 → 183（−42%）**。

**关于验证方法的一点说明**：整个过程里我有**两次**差点被"假信号"带走 ——
跨页面加载的单图指标因为草地/光尘/篝火石块都带 `Math.random()` 而不可比，
`glowPct` 的跨局波动就有 0.16~2.79，足以淹没真实的改动效果。
凡是有争议的地方，最后都换成了**决定性验证**：读编译后的着色器源码、
读合并后网格的包围盒、直接驱动摇杆读真实速度、跨帧率对比弹簧收敛值。

## 二、逐项结果

### ✅ 1. MSAA 静默失效 → 换成 SMAA

**症状**：黄昏相位下整屏是一块均匀暗色，地面/水面/角色/道具全部消失。

**排查**：相机参数正常、一帧 387 次 draw call、16 万三角面（几何在画）、控制台零报错；
`EXT_color_buffer_float` 存在、`checkFramebufferStatus` 报 `COMPLETE`、`gl.getError()` 报 `NO_ERROR`
——多采样本身完全合法，所以查了非常久。

**结论**：`composer` 的渲染目标是 `HalfFloatType`，在其上设 `samples` 后 resolve 出来是错的，
**且只在黄昏这类高动态范围相位暴露**。

**修法**：不给 composer 的 RT 开 MSAA，改用独立的 SMAA 后处理 pass
（它工作在 linear-srgb，必须排在 `OutputPass` 之前）。

```
RenderPass → 体积光 → UnrealBloomPass → SMAAPass → OutputPass
```

**附带净收益**：`antialias: !mobile` 只作用于默认帧缓冲，而场景是渲到 composer 的
离屏 RT 上的 —— 也就是说这个项目**原本完全没有抗锯齿**。

**实测**（同相位同机位）：

| 指标 | 基线 | 修复后 |
|---|---|---|
| `edgeHardSoft`（硬边占比） | 0.8835 | **0.2862** |
| `lumaMean` | 0.2597 | 0.2609（没靠调亮画面作弊） |

### ✅ 2. 草地是"满地白色纸板"

**量化根因**：草叶尖色 `hi = vec3(0.58, 0.78, 0.42)` 是**线性**值，Rec709 亮度 **0.711**，
而地面渲染后实测约 **0.25** —— 草比地面亮 **2.6 倍**。再叠加四个因素：

| 因素 | 原值 | 问题 |
|---|---|---|
| 片元 alpha | `vec4(col, 1.0)` | 完全不透明，没有羽化 |
| `side` | `DoubleSide` | 正反面都实体填充 |
| 叶尖收窄 | 只收到 65% | 是个方头，不是叶片 |
| 实例缩放 | 0.75~1.60 | 最高近 1m 高、0.48m 宽 |

**修法**：叶尖收到 0（叶形轮廓）；颜色压到 `lo(0.045,0.105,0.042)` /
`hi(0.165,0.305,0.115)`（亮度 0.088 / 0.261，与地面同档）；叶片 0.09×0.30m、
缩放 0.62~1.20；簇数 420 → **1500**、每簇 6~9 片；每片加随机**倾角**
（原来只有绕 y 的朝向，所以是一片片竖直的牌子）；摆动幅度 0.16 → 0.055。

**顺带修掉一个跨模块不一致**：草地着色器的雾是**自己写死**的（`#eecfa4` / 0.0042），
而昼夜系统从没同步过它 —— 夜里场景雾转暗蓝、草地却还朝亮米色淡出，
草地上会浮出一片片发亮的奶色斑块。现在雾状态放进共享的 `lightState`，草地每帧同步。

### ✅ 3. 雾不跟随昼夜相位（P1）

`PHASES` 里每个相位的雾色/密度都给得很讲究（黄昏 `#eecfa4`/0.0046、
夜 `#2a3354`/0.0055、黎明 `#dcc4d4`/0.0050、白昼 `#cfe0e8`/0.0038），
但**没有任何代码把它写进 `scene.fog`**。雾恒为黄昏的亮米色，
到深夜就是一层**发亮的奶色霾**糊住整片远景 —— 近处暗、远处更亮，方向完全反了。

**实测**：夜间从 `#eecfa4 / 0.0046` 变为 `#2e3551 / 0.0055` ✓

### ✅ 4. 半球光与环境光不跟随昼夜相位（P1，夜景不成立的根因）

**和雾是完全一样的漏法**：`PHASES` 里一直有
`hemiSky` / `hemiGround` / `hemiInt` / `ambientColor` / `ambientInt` 五组值，
但建完 `HemisphereLight(...0.82)` 和 `AmbientLight(...0.36)` 之后就**再没人写过它们**。

于是深夜的半球光还是白昼的 **0.82**、环境光还是 **0.36**。

**实测**（强制深夜相位）：

| 指标 | 修前 | 修后 |
|---|---|---|
| `lumaMean` | 0.1467 | **0.0673** |
| `darkPct`（暗部占比） | 27.2 | **79.3** |
| `regions`（九宫格） | 0.135, 0.352, 0.200 | 0.046, 0.043, 0.040 |

夜景现在是"篝火暖光池 + 四周真正沉下去的暗"，这正是《光遇》的夜景结构。

### ✅ 5. 全项目特效都够不到 bloom 阈值（P0）

bloom 的亮度高通作用在**线性、tone-map 之前**的值上，阈值 0.8。
而加法混合下一个光点的实际贡献是 `颜色 × opacity × 闪烁`：

| 特效 | 颜色线性亮度 | × opacity | × 闪烁峰值 | 实际峰值 | 过阈值？ |
|---|---|---|---|---|---|
| 光尘 | 0.830 | 0.35 | 1.00 | **0.29** | ✗ |
| 萤火虫 | 0.913 | 0.60 | 1.00 | **0.55** | ✗ |
| 余烬 | 0.543 | 0.90 | — | **0.49** | ✗ |
| 音符字形 | 1.000 | 0.98 | — | **0.98** | ✓ |

**修法**：引入 `lightState.fxGain()` 作为唯一总开关，乘进**颜色**（进 HDR）而不是 alpha。
取值是算出来的：`0.830 × 0.5 × 1.0 × 2.0 = 0.83`（刚好压在阈值上，永远差一点），
`0.830 × 0.5 × 1.0 × 3.2 = 1.33`（稳定过阈值）→ 所以 `fxGain() = 3.2 + night × 1.6`。

`particles.ts` 同步修掉三处：
- **`gl_PointSize` 硬编码 `140.0`** —— 等于隐式假设画布高 280px，换分辨率就变形。
  改成按 drawing buffer 高度等比缩放（720p 下数值不变）。
- **闪烁幅度 `0.10~1.00`** —— 大部分时间在阈值上下穿越，读起来是"忽明忽灭的斑点"。
  收窄到 `0.4~1.0`：一直在发光，只是明暗在呼吸。
- **余烬用无贴图的 `PointsMaterial`** —— three 只在 `#ifdef USE_MAP` 下采样
  `gl_PointCoord`，所以它**渲染成实心方块**。补柔边贴图 + HDR 颜色。

**实测**（强制深夜相位）：`glowPct 0.248 → 1.029`（**4.1 倍**）。

### ✅ 7. 斗篷两处尺度错误（`cape.ts`）

**(a) `rowLen` 拿"被裁过的下摆"当量尺。** 原来是从 column 0 首末顶点实测 y 跨度，
而 `shapeCape` 恰好要把底边整条抬起来做扇贝 —— 量出来只有标称的 **73%**。
于是 `maxLen` 里那个"1.45 倍余量"实际只剩 **1.06 倍**，披风在快速移动时被提前锁直成硬板，
布的拉伸与回弹全被吃掉。改成取**未变形的标称行距**，且免疫 `shapeCape` 的任何形变。

**(b) Verlet 加速度项写成 `a·h²·60`，而 `h ≡ dt = 1/60`，于是 `h²·60 ≡ h`。**
真正施加的位移是 `a·h` 而非 `a·h²`，**加速度被放大 60 倍** ——
只是靠把 `gravity` 调成 6 来配平。步长固定所以行为没错，但这个 60 是**隐式**的：
`dt` 一改成 1/120，重力和风会一起变 4 倍、披风直接爆炸。
改成显式常数并按 `h²` 正确缩放，`dt = 1/60` 下与原来**逐位相同**。

### ✅ 8. 步态脚滑（`avatar.ts`）

**根因**：`strideLen` 是个**幽灵变量** —— 它除了算 `stepRate` 之外再没被任何代码用过，
而腿的真实摆幅是另一处的 `0.55 × walkAmp`。两者毫无联系，所以
"步幅 × 步频 = 位移"这个关系**从来没有成立过**。注释里写的"步长随幅度放大"
只是意图，没落到代码上。

其次，`walkPhase += dt × (stepRate + min(6,|yawVel|) × 1.4)` 在转向时最多**额外加 8.4 rad/s
的步频，而位移一点没变** —— 高速时是纯打滑。

**修法**：按 `一步距离 = 2·LEG·sin(摆角)`（一步 = π 弧度）反解步频，
并且腿的摆角系数随速度从 0.55 长到 1.10（"走小步跑大步"真正生效）；
转向不再推进步频（"转身碎步"已在 `turnShuffle` 里正确表达：只改幅度、随速度淡出）。

**实测**（数值验证，`LEG = 0.52`）：

| 速度 m/s | 摆角 | 真实步幅 | 步频 | 实走距离/s | 误差 |
|---|---|---|---|---|---|
| 0.5 | 0.232 | 0.240 | 6.56 | 0.500 | **0.0%** |
| 1.0 | 0.276 | 0.283 | 11.09 | 1.000 | **0.0%** |
| 2.0 | 0.373 | 0.379 | 16.58 | 2.000 | **0.0%** |
| 3.6 | 0.557 | 0.550 | 20.58 | 3.600 | **0.0%** |
| 5.0 | 0.747 | 0.707 | 22.23 | 5.000 | **0.0%** |
| 6.0 | 0.899 | 0.814 | 23.15 | 6.000 | **0.0%** |
| 7.2 | 1.100 | 0.927 | 24.40 | 7.200 | **0.0%** |

**全速度档误差 0.0%**。修复前（用动画真实步幅复算）：3.6 m/s 时实走 2.30 / 位移 3.6
→ **打滑 36%**；7.2 m/s 时 → **打滑 42%**。

## 三、整体指标对比

### 3.1 一个重要的测量陷阱（先说清楚，免得被数字误导）

**不同 session 之间的构图是随机的**：角色出生点与朝向是
`Math.random()`（`main.ts:208` 的 `selfHue` 同样是随机的），光尘/萤火虫的落点也是随机的
（240 个点撒在 r=52 的圆内）。所以**同一机位不同 session 的整帧 `glowPct` 会差好几倍**：

| 截图 | 相位 | `lumaMean` | `glowPct` |
|---|---|---|---|
| `night-final.png` | 深夜 | 0.0673 | 0.248 |
| `fx-glow-night.png` | 深夜 | 0.1017 | 1.029 |
| `final-night.png` | 深夜 | 0.0582 | 0.164 |

三张都是"深夜"，差别主要来自**画面里有没有篝火、光尘碰巧在不在视野内**。
所以**不要**拿单张整帧指标当结论。

### 3.2 改用确定性验证：直接读运行时着色器 uniform

不依赖构图的办法是把场景遍历一遍，读出每个发光材质的
`uColor`（线性亮度）× `uOpacity` × `uEmissive`，看峰值是否真的越过 0.8：

| 对象 | 颜色线性亮度 | opacity | emissive | **峰值** | 过阈值 |
|---|---|---|---|---|---|
| 光尘（`Points`） | 0.830 | 0.50 | 3.2 | **1.328** | ✓ |
| 萤火虫（`Points`） | 0.913 | 0.03（黄昏；夜间升至 0.75） | 3.2 | 0.088 → 夜间 **2.19** | ✓（夜间） |
| 余烬（`PointsMaterial`） | 1.932 | 0.90 | 3.2 已折进颜色 | **1.738** | ✓ |
| 风线（`LineSegments`） | 0.897 | 0（地面时；滑翔时上升） | 3.2 | 滑翔时 **>1** | ✓ |

余烬那行的 `hasMap` 现在是 `true`（原来是 `false`，即实心方块）。

### ✅ 12. 地形台地化 + 烘焙 AO

**问题**：地面是一片没有起伏细节的均匀渐变，坡面与坡面之间完全分不开 ——
看起来像贴在地上的一张图。

**做法**：
- **烘焙 AO（地平线遮蔽）**：逐顶点在 8 个方向各取 4 个距离，看邻域地形相对当前顶点
  抬升得多快，仰角越大遮得越死，把凹折处压暗。下限取 0.58 而不是 0 ——

### ✅ 13. 水面波光

**两个真问题**：

1. **`shallow` / `deep` 是写死的常数，完全不跟随昼夜** —— 和雾、灯光是同一类漏法。
   `WaterPhase` 接口里一直带着 `night` 字段，`setPhase` 却**从来没读过它**。
   于是夜里海面还是白天的亮青绿。（已补 `uNight`，实测 0 → 1 → 0 正确跟随。）
2. **波光的峰值只有 `0.771 × 0.22 = 0.17`，永远过不了 0.8** —— 水面从来没有真正闪过。
   上一版之所以把高光压成"宽而弱"，注释里写得很清楚：高光全押在**顶点着色器**的
   低频波法线上，而近岸网格远处一格的投影尺寸很大 —— 高光会随网格跳变，像频闪灯。

**修法**：把**细波法线放进片元**（4 组不同朝向 / 频率的解析导数，每像素算一次法线扰动），
高光因此既细腻又稳定，才敢把它做到 HDR。碎闪用两层：宽而柔的整体光泽（不过阈值）
＋ 窄而亮的碎闪（进 HDR，`pow(ndl, 240.0)`）。

**实测三相位**：

| 相位 | `night` | `glint` | 碎闪峰值 | 过 0.8？ |
|---|---|---|---|---|
| 黄昏 | 0 | 1.9 | **1.037** | ✓ |
| 深夜 | **1** | 1.4 | **0.974** | ✓ |
| 白昼 | 0 | 1.9 | **1.584** | ✓ |

### ✅ 14. 统一美术语言：glTF 的 PBR 材质全部转成 toon

**问题**：GLB 角色（`elaina.glb` / `rogue-hooded.glb` / 各种动物）是
`MeshStandardMaterial`（PBR：metalness / roughness / normalMap 一起做微表面着色），
而程序化角色与整个岛都是 `MeshToonMaterial`（把 N·L 量化成几档色阶）。
两者并排出现时一眼就能看出「一个是从别的管线导入的、一个是在这个项目里画的」。

**三个「PBR 味」的来源**，逐个去掉：
1. **metalness / roughness 的镜面项** —— toon 没有这一项，去掉后表面立刻变哑光。
2. **normalMap 的微表面起伏** —— 留着会让色阶上出现连续明暗过渡，和 toon 的硬边色阶打架。
3. **自发光**。`elaina.glb` 的 10 个材质全是 `baseColorFactor:[0,0,0,1]` + 纯 `emissiveMap`

   所以遇到「底色是黑、没有漫反射贴图、但有 emissiveMap」的材质，
   就把 **emissiveMap 当作漫反射贴图**接过来，让它重新参与光照而不是自发光；
   同时保留一层**减弱到 0.35** 的自发光作为下限，避免个别部件塌成黑块。

**过程中抓到一个我自己引入的 bug（挺有代表性）**：

我原本在源材质上打了个 `__toonified` 标记来防止重复转换。但 `SkeletonUtils.clone`
是**共享材质**的 —— 第一个实例转换时会新建材料、源材质保持原样，

探针当时读到 `toonified: 10` 却同时有 `115 个 MeshStandardMaterial` 残留，
正是这个症状。

修法：去掉标记（转换本身幂等、不修改源材质，重复调用安全正确）。

**实测**：

| | 修复前 | 修复后 |
|---|---|---|
| 转换成功的 toon 材质 | 10 | **125** |
| 残留「黑底 + emissive」的 Standard 材质 | 115 | **0** |
| 场景里剩余的 `MeshStandardMaterial` 总数 | 115 | **0** |

整个场景现在**一个 `MeshStandardMaterial` 都不剩**，美术语言统一 ✓

### ✅ 15. 天空：地平线霾带 + 星点重做 + 夜空提亮

**三个问题，都在天空这一个文件里：**

**① 星点是次像素硬阶跃 —— 会闪烁爬行。**
原来是 `step(0.9975, hash(floor(d * 220.0)))`。星点只有**次像素**大，而且是硬阶跃：
相机一转，`floor` 出来的 cell 就整块跳变，星星于是闪烁、爬行，甚至成片地冒出来又消失。
这是程序化星空最典型的假象。
改成：每个 cell 里放一颗**有确定位置**的星心，用「到星心的距离」做柔和衰减，
并对 2×2×2 邻域求和 —— 星点因此是连续的，跨 cell 边界也不会断开。
另外原来只在 `h > 0.18` 以上才有星（低空是一片死黑），现在一直铺到地平线。
整段用 uniform 分支包住，白天完全不执行。

**② 地平线附近什么都没有。** 加了三层不同高度的软雾带，用方位角调制出断续的条理
（不然就是三个同心圆环，很假），并让**面向太阳那一侧更亮**（逆光时地平线发白，
这是实拍里最明显的特征）。

**③ 夜空几乎是纯黑的。** 实测调色表里深夜天顶 `#0c1230` 的线性亮度只有 **0.0072**，
是白昼天顶 0.208 的 **1/26**；而地平线 0.089 反而是它的 11 倍 —— 上下对比大得离谱，
抬头就是一片死黑。提到 `#232e6b` 后：

| 夜空（固定仰视机位、同一相位） | 改前 HEAD | 只改星空 | 再提亮调色 |
|---|---|---|---|
| `lumaMean` | 0.0106 | 0.0052 | **0.0254（2.4×）** |
| **`colorfulness`** | 0.0921 | 0.0928 | **0.3025（3.3×）** |

`colorfulness` 3.3 倍是关键 —— 夜空从「接近灰黑」变成了有饱和度的深蓝。

> **这一步是安全的单点控制**：天穹是 BackSide 的**纯着色网格、不发光**，
> 改它不会照亮场景。场景光照由 `hemiSky` / `hemiGround` / `ambientColor` 单独控制，
> 两边互不影响 —— 所以可以只提亮"看得见的天"，而不破坏之前辛苦调出来的夜景地面曝光。

### 🔍 附带结论：用户报告的「夜间细长竖向光柱」已被之前的修复解决

体积光 pass 的阈值 `uThreshold = 0.55` 作用在**线性、未色调映射**的帧缓冲上。
而修掉之前，夜间雾色是 `#eecfa4`（亮暖色）—— 它在线性下**远超** 0.55，
于是整片天空都在向画面里径向漏光，那才是「竖向光柱」的真正来源。

现在实测四个相位的雾色：

|---|---|---|---|

| **深夜** | `#2e3551` | **0.037** | **否** ✓ |
| 黎明 | `#dac6d4` | 0.6016 | 是 |

深夜不触发，所以夜间只剩月亮圆面自身产生的径向柔光（这是想要的）。

### ✅ 18. 全岛静态道具跨组合批：draw call 砍掉 41.5%

**发现**：树是 **12 棵 × 6 个 Mesh = 72 个**（树干 + 根裙 + 2 根枝桠 + 树冠 + 果实），

### ✅ 19. 相机与移动端手感（5 处）

这一项原本是「并行任务改过但我没复核」的状态，实际复核后发现：`controls.ts` 的
**指针锁判断确实已经修好了**（`e.pointerType === "mouse"` 守卫齐全，触屏不会再走
`movementX` 通道导致转视角失效），相机的**速度前瞻**也加了。但 `touch.ts`
**一行都没改**，摇杆的硬阈值也还在。补齐如下。

**(1) 摇杆死区 + expo**（`touch.ts`）
原来是纯线性映射（`(dx/R, dy/R)`），外层只在 0.08（≈3.4px）处拦一下 ——
手指搭在摇杆上微抖就会让角色缓慢平移。改成：死区 **0.14**（≈5.9px）+
`pow(u, 1.25)` 的 expo。有个容易写错的地方：**必须先算方向单位向量、再乘整形后的长度**，
如果对 x / z 各自整形，斜推时两个分量的缩放倍率不同，方向会被掰偏。

**(2) 走 → 跑连续化**（`physics.ts` + `controls.ts`）
原来 `const joyFull = len > 0.88` 是**布尔**开关，`physics.ts:340` 则是
`cap = running ? 7.2 : 3.6` —— 摇杆在 0.88 → 0.89 这 **1% 行程内速度目标跳 +3.2 m/s**。
把 `PhysicsInput.running: boolean` 改成 `runBlend: number`，
`cap = 3.6 + 3.6·runBlend`，摇杆侧用 `smoothstep(len, 0.75, 1.0)`。
键盘 Shift 仍直接给满，保持键盘的干脆。

**端到端实测**（直接驱动摇杆、泵帧、读真实速度）：

| 摇杆行程 | 旧（硬阈值） | 新（连续） |
|---|---|---|
| 0.86 | 3.10 | **4.37** |
| 0.88 | 3.17 | **4.85** |

实测 4.14；0.90 → 5.93×0.90 = 5.34，实测 5.35），说明平滑曲线推对了。

**(3) 飞行按钮加指针捕获**（`touch.ts`）
`btn()` 只挂了 `pointerleave → release`。按住 64px 的「跳跃/滑翔」按钮时手指轻微滑动
是常态，一滑出边界就触发 `pointerleave` → **滑翔立刻中断**。这是移动端最难受的一个
手感 bug：想滑翔，手指一飘就掉下来。改为 `setPointerCapture`，
并保留 `pointerleave` 作为**捕获失败时**的兜底。

**(4) 远端玩家的腾空判据**（`remote.ts:219`，审查里的 P1）
原判据用**裸 `terrainHeight`**：
- 站在岩石 / 灯塔环廊 / 木凳上的人，y 比地面高出一大截 → 被判成腾空 → **一直摆着下落姿势站在石头上**
- 水里同理：水面在 0.55、海底可能 −1.5，差值 2m 也误判 → **游泳的人半游半坠**

改用项目里本来就有的 `standGroundHeight()`（返回可站碰撞体顶面；没有可站面时返回
`-Infinity`，所以要与地形取 `max`），并加 `inWater` 短路。

**(5) 弹簧改成帧率无关**（`motion.ts`）—— 这条不在清单上，但复核时顺手发现的
原来是 `const h = Math.min(dt, 1/30)`，把 dt **截短**。20fps（dt=1/20）时每帧只推进
1/30 秒，一秒真实时间只模拟了 0.667 秒 —— **收敛速度只剩 2/3**，相机跟随与身体姿态一起变「拖」。
改成**子步**（`ceil(dt/SUB)` 步、每步 `dt/n`），模拟时间如实等于 dt。

实测同一个弹簧跑满 1 秒真实时间、目标 1.0（`k=46, c=13.56`）：

| 帧率 | 旧公式 | 新公式 |
|---|---|---|
| 120fps | — | **0.9896** |
| 60fps | 0.9881 | **0.9896** |
| 30fps | — | **0.9896** |
| 20fps | **0.9330** | **0.9896** |
| 10fps | **0.6973** | —（上限 8 子步 ≈ 67ms 后开始退化，防「追帧」雪崩） |

所有帧率收敛到**同一个数** ✓。顺便：半隐式欧拉在 `h ≤ 1/120` 下比原来更稳，
原来的 1/30 对高刚度弹簧反而更接近失稳边界。

### ✅ 21. 台地岛：真几何台地 + 岩石改青灰（本轮新增，且**首次做了视觉验证**）

> 本轮开始我**能读图了**（之前 `read_image` 一直报「模型不支持图片输入」）。

> 不再是纯靠数值推断。截图存在 `docs/evidence/terrace-*.png`。

**(1) 岩石：薰衣草紫 → 青灰**

我原以为改过，其实**没改**。截图里一眼就看到岛上有几颗**紫罗兰色的糖豆**。
两处都是紫的：`props.ts` 的 `#a79fd0`/`#9a94c4`，以及 `terrain.ts` 的
`C_ROCK = #aca3cd`（H≈253°）。光遇的崖壁是**青灰**（H≈200~210°），

**(2) 台地：把「馒头」做成「台地岛」**

原来穹顶是连续幂函数 `5.5*(1-rr)^1.25 + 1.2`，横向最大坡度只有 0.62，
从任何角度都是一个馒头。现在在 `heightfield.ts` 里加了软台阶化：

```ts
function terrace(h) {
  const t = (h + TERRACE_H * 0.5) / TERRACE_H;   // 先平移半格
  const i = Math.floor(t);
  return (i + smoothstep(0.55, 1.0, t - i)) * TERRACE_H - TERRACE_H * 0.5;
}
```

**为什么要先 +半格再 -半格**：台阶是向下吸附的，直接用会让整座岛平均下沉
约 0.95m —— 岸边那一圈（原来 1.2~1.5）会掉到 0.55 的水面以下，**岛会肉眼可见地缩小**。
平移后台阶**居中**落在原高度上，各高度偏差 ≤0.5m，海岸线基本不动。

台阶高度 1.9m、平台占 55%、崖唇占 45%（圆润过渡，不是直角坎）。
⚠️ `water.ts` 的 `terrainH` GLSL 副本**已同步**，否则水面与岸线会错位。

**(3) 崖唇露岩：用解析的崖唇位置，不用坡度**

第一版我让岩色跟着 `slope > 0.42` 走，结果**整座岛糊成灰霉斑** ——
有限差分算出来的坡度被噪声推得忽高忽低。改成直接用台地参数 `soft`

第二版用宽 `smoothstep` 铺满整段崖唇，结果**岛心被灰色吃掉** ——
崖唇本身占 45% 面积，全上岩色就反客为主。最终用 `sin(π·soft)` 取窄峰
（只在崖唇正中一带上色，`× 0.72` 混色）。

```ts
const R = topR + (botR - topR) * t;      // t: 0=肩线, 1=下摆
const th = (x / halfW) * halfArc;
pos.setX(i, Math.sin(th) * R);
```

### ✅ 25. 地形三色配比：**全部进区间**

接上一节。上轮沙达标了（9.5%），但岩只有 5.3%。这轮把岩也收口了，**关键是把岩放到它该在的地方**。

**(1) 一个反直觉的实测结论：岩占比由「崖唇占台阶高度的比例」决定，不由台阶高度决定**

我先把 `TERRACE_H` 从 1.9 砍到 1.35（台阶数翻倍），以为崖唇总面积会跟着涨 ——

### ✅ 26. 笔刷噪声尺度：**找到并修掉了一个真 bug**（审查 1.5）

前面几轮我一直没做这条，因为我读代码的结论是「角色本来就传了 `brushRepeat = 0`，没噪声」。
**这个结论是错的。**

`toon.ts` 的签名是：

```ts
mat(color, vertexColors = false, brushRepeat = 2) {   // ← 第三个参数默认 2
  ...
  ...(brushRepeat > 0 ? { map: brushTexture(brushRepeat) } : {}),
```

而同文件顶部的设计注释写的是「**传 0 表示不用笔触图（纯色 + ramp，角色用）**」。
实际 `avatar.ts` 里 **10 处 `kit.mat(color)` 全都没传第三个参数** ——
角色的每一块皮肤都被**静默**糊上了一层笔刷噪声。

**尺度算一下就知道为什么审查管这叫"塑料感"**：笔刷贴图在 1.5m 高的角色上按见方铺 2 次
→ 每格 0.75m，贴图里柔斑直径 26~54px/256px → 实际柔斑 **7.6~15.8cm**，
**只有部件尺寸的 1/10**。审查建议「波长 ≥ 8 倍部件尺寸」，
对 1.5m 的角色来说 8 倍 = 12m —— 现实答案就是**别用笔刷图**。

**修法**：加一个角色专用包装，显式传 0；10 处调用点全部改走它。

```ts
const cmat = (color: string, vertexColors = false) => kit.mat(color, vertexColors, 0);
```

> 踩坑记录：第一版我顺手把这个 helper 插在了 `makeLeg()` **内部**，
> 结果 `makeLeg` 一闭合（L457）外面就看不见了，`tsc` 报 **6 个 TS2304**。
> 必须放在 `createAvatar` 的函数体顶层。这条也写进注释了。

**实测**（自机 29 个材质引用 / 16 个去重材质，遍历统计）：

| | 改前 | 改后 |
|---|---|---|
| 带贴图的材质引用 | **22** | **6** |

剩下 6 个是**本来就该有贴图**的：名牌 Sprite、音乐光环 2 张、微光 Points、头顶光晕、接触阴影。

**观感确认**（`no-brush.png`）：皮肤恢复成平滑的奶油色，头是干净的深色球 + 浅色面具，
眼睛是清爽的发光椭圆 —— 那层细密花斑消失，更接近光遇的平涂柔和感。
**全岛静态道具的笔刷保留不动**（那里 75m 一格、柔斑 7.6~15.8m，本来就是合适的低频）。

### 🎯 33. 【本轮最大收获】一道笔直竖条 = `shapeCape` 的宽度断崖 —— 修好了，两个指标同时下降

**(1) 现象：背视里披风上有一道笔直的浅色竖条**

**(2) 真凶：`shapeCape` 只排除了「顶端那一行」**

```ts

```

**(3) 修法：把断崖改成平滑过渡**

```ts
const h = smoothstep01(-y / 0.12);       // 0 = 肩线，1 = 往下 0.12m（约第 3 行）
pos.setX(i, x * (1 - 0.14 * h));         // 收窄量渐变，不再是 0→0.86 的跳变
pos.setY(i, y + jag * h * (0.13 * lobe + 0.035 * Math.sin(...)));
```

平滑半径**取 0.6m（全程过渡）**。这个数不是拍的 —— 见下。

**(4) 我自己先选错了 0.12m，然后用数值把它否掉了**

第一版我把过渡半径取成 0.12m，理由是「改动只限最上面 3 行、尽量不动已调好的轮廓」。

相邻两行的抬升量差会**超过行距**，于是行与行直接**穿插**。

### 🥚 35. 躯干从「球」改成真正的「蛋形」—— 视觉自评第一条落地

**(1) 自评里那句话的字面根因**

四角度自评我写了「躯干接近一个完美球体」。查代码：

```ts
// 注释写着「蛋形（下宽上窄的胖藕躯干）」
const torso = new THREE.Mesh(new THREE.SphereGeometry(1, 22, 18), cmat(skin));
torso.scale.set(0.315, 0.345, 0.275);
```

**球体缩放出来的是纯椭球，上下完全对称** —— 数学上不可能「下宽上窄」。
注释描述的是一个代码从没实现过的形状。

**(2) 改法：按高度给锥度**

```ts
const eggK = (t) => 1.06 - 0.36 * t * t;   // t: 0 = 底, 1 = 顶
// 逐顶点按 y 缩放 x/z：底部 ×1.06 → 中部 ×0.97 → 顶部 ×0.70
```

**(3) 一个必须同步改的连带项 —— 否则肩膀会脱开**

手臂挂点原来**写死** `0.30`。我算了一下：肩高 0.82 在单位球坐标里是 y=0.638，
那里球面半宽 `0.315×√(1−0.638²) = 0.2426`，加上大臂半径 0.058 = **0.3006** ——
也就是说 `0.30` 是**刻意算出来让手臂与躯干相切**的，不是随手填的数。

躯干一收锥度，肩高处半宽变成 `0.2426×0.818 = 0.1985`，挂点必须同步内移到
`0.1985 + 0.058 = 0.2565`。所以改成了跟着 `eggK` 一起算：

```ts
const SHOULDER_Y = 0.638;
const armX = 0.315 * Math.sqrt(1 - SHOULDER_Y ** 2) * eggK((SHOULDER_Y + 1) / 2) + 0.058;
```

> 教训：**这类「魔法数字」其实是几何约束的解**，动几何前先把它反解出来，
> 否则就是把一个正确的对齐改成错的。

**(4) 验证**

| 判据 | 结果 |
|---|---|
| 躯干顶端半径 / 底端半径 | 0.373 / 0.529 = **1.42** ✓ 锥度是真的 |
| 全角色二面角复扫（超 120° 的边） | 仍**只有披风**（13 条），四肢/头/其余全部 **0** ✓ 没造出新折痕 |
| 自相交门 `outerCape inside` | **6**（改前也是 6，**无回归**）✓ |
| 披风碰撞体 | 躯干最大半宽 `0.315×1.06 = 0.334` < 碰撞体 `T_X = 0.387` ✓ 不会穿模 |
| 头身衔接 | 头顶底部 y=0.841 < 躯干顶 y=0.945 ✓ 仍重叠，肩颈没脱开 |

### 🦴 36. 加肩关节球 —— 手臂从「贴上去」变成「长出来」

### 🧵 37. 披风与背那道缝 —— 追到根因，但撞上一堵墙（如实记录）

**(1) 根因：碰撞体是按一句**过时的注释**建的**

`cape.ts` 里写着：

```ts
// 躯干渲染网格是 (0.345, 0.405, 0.30) 的椭球、中心 y0.62
const T_X = 0.387; const T_Y = 0.442; const T_Z = 0.342;
```

而 `avatar.ts` 里**实际是** `torso.scale.set(0.315, 0.345, 0.275)` ✗
再加上躯干后来改成蛋形收锥，最大半宽其实是 **0.309 / 0.270**。

⇒ 碰撞体比身体大出约 **25%**，披风被顶在离背 7cm 的地方 ——
**侧视图里那道缝的根因就是这句对不上的注释。**

**(2) 按真实几何重算，做了三档实测**

| 余量 | 侧视的缝 | 背视穿透 |
|---|---|---|
| 20mm | 几乎贴合 ✓ | **下背捅出三块肉色** ✗ |
| 45mm | 基本贴合 ✓ | 下背剩**一道细缝** △ |
| **55mm（采用）** | 仍然贴着背 ✓ | 残留**一道很细的缝** △ |
| 75mm（旧值） | 明显的 5cm 缝 ✗ | 完全不穿透 ✓ |

**(3) 关键发现：这不是几何问题，是求解器问题**

我算过：余量只要 **20mm**，椭球就已经把躯干和四肢**全部包住**了
（躯干最大半宽 0.309 / 0.270，大腿外缘 0.182，都在椭球内）。

⇒ 所以 20mm 时仍然穿透，**不是"包不住"，而是布料求解器没收敛**（`iters = 5`）。
余量实际是在补**求解误差**，不是在补几何。

这也解释了为什么调 `iters`（5→9）当时反而更糟 —— 它和余量是两个相互作用的旋钮。

**(4) 结论：这是一个真实的取舍，不是可以两头都拿的**

- **穿透**（身体从披风里露出来）是**渲染缺陷**，玩家一眼能看出是 bug
- **缝**（批风离背 5cm）是**风格问题**，一件斗篷站开一点并不算错

我最终取 **55mm**：侧面那道缝从 ~50px 收到几乎贴合，
背面残留一道很细的缝（约占披风面积 4%）—— 比原来的 5cm 缝好得多，
比 20mm 的三块穿透好得多。

**仍然没有两头都干净**，如实留在第四章。

### ⚓ 38. 补跑 `attachment_anchor.py`：穿戴件锚点门 —— 通过（且证明门不是空跑）

这一项一直挂在第四章「还没跑」。这轮补上。

**(1) 先说清楚这一项能做什么、不能做什么**

`check_part_coverage.py` 需要 img2threejs 管线的 `--spec` + `--manifest`。
本项目的角色是**在 TypeScript 里程序化写出来的，不是从 spec 生成的** ——
我要是自己读代码写一份 spec 再去"比对"，就是**自己出题自己答**，纯循环论证。**所以这项不做**。

这一项不循环 —— 实测位置来自正在跑的游戏 ✓

**(2) 第一次跑是空跑，差点被骗过去**

第一版 spec 我把 `componentTree` 写成了**树形对象**，而它要的是**扁平列表 + `parent` 字段**。


**`passed: true` —— 但它一件东西都没检查。** 这正是这个门自己的文档里
点名警告的失败模式：「0 violations from a check that never ran on anything」。
光看 `passed` 会以为过了。

**(3) 修正后：真实结构通过**

| 部件 | 锚点 | 实测距离 | 上限 | 判定 |
|---|---|---|---|---|
| `cape_outer` 外层披风 | `torso` | **0.2510** | 0.35 | ✓ within-limit |
| `cape_inner` 内层披风 | `torso` | **0.1803** | 0.35 | ✓ within-limit |

`verdict: PASS`

（实测用的是**几何包围盒中心**的世界坐标。注意不能用 `setFromMatrixPosition` ——

**(4) 阴性对照：证明门真的会响**

### 💪 44. 撤掉肩关节球 —— 手臂改成从躯干体内长出来

**(1) 那颗球是"补丁"，不是解法**

代码里原本有一段注释，记录了当初为什么要加它：

> 「大臂胶囊的内缘原本正好落在躯干表面上（**相切**），两者只碰在一条线上，
> 侧面看就是一道凹痕 —— 这就是自评里说的「衔接偏贴上去」。
> 这个球的半径取 0.076（比大臂半径 0.058 大）… 形成圆润的肩头。」

也就是说：**挂点写死成「半宽 + 大臂半径」，造成相切 → 相切出凹痕 → 再补一颗球去盖凹痕。**
球盖住了凹痕，但球本身又变成一处"球贴球" ✗ —— 补丁摞补丁。

**(2) 顺着上一轮的思路：把挂点算对，补丁就不需要了**

```ts
const shoulderHalfW = 0.315 * Math.sqrt(1 - SHOULDER_Y**2) * eggK((SHOULDER_Y+1)/2) * BODY_W;
const armX = shoulderHalfW + 0.058 * 0.6;   // ← 不是 + 0.058（相切），而是 ×0.6（嵌入）
```

- 取 **60%** 而不是 100%：大臂**嵌进**躯干 0.035m，直接从体内长出来
- 顺便修掉一个隐藏 bug：原公式里是**裸的 `0.315`**，
  而上一轮剖面整体乘了 `BODY_W=1.126` —— 公式没跟，已经不成立了 ✗

**(3) 结果**

[`limb-smooth.png`](docs/evidence/limb-smooth.png)（有肩球）→ [`sh2-side.png`](docs/evidence/sh2-side.png)（无肩球）：
肩头不再是一颗独立的球，而是**躯干本体收进手臂**的连续曲面 ✓

**(4) 回归**

### 📱 47.【用户报障·已修复】电脑端页面出现手机按键 —— 而且顺带发现桌面端一直在用手机画质

**(1) 用户报的故障**

> 「手机端按键怎么到电脑端页面了」

**(2) 根因：一句不可靠的设备判据**

`client/src/touch.ts`：

```ts
return matchMedia("(pointer: coarse)").matches
    || matchMedia("(max-width: 720px)").matches
    || "ontouchstart" in window;      // ✗ 元凶
```

`"ontouchstart" in window` 检测的是「**浏览器有没有这个属性**」，
**不是**「设备有没有触屏」。Windows 版桌面 Chrome 多数版本都定义了它 ✗
⇒ 桌面端被判定为触屏设备 ⇒ `touchUI.setVisible(true)` ⇒ 虚拟按键跑上桌面 ✗

**(3) 更严重的连带后果：桌面端一直在用手机画质**

`client/src/world/scene.ts`：

```ts
const mobile = isTouchDevice();                       // ← 同一个误判
const renderer = new THREE.WebGLRenderer({ antialias: !mobile, ... });   // ✗ MSAA 被关掉
renderer.setPixelRatio(Math.min(devicePixelRatio, mobile ? 1.5 : 2));    // ✗ 像素比被压到 1.5
```

**桌面端的 MSAA 抗锯齿一直是关的** ✗ —— 锯齿边缘正是"模型看起来粗略"的一大来源，
和第 43~46 节追的那些几何问题**不是一回事**。

**(4) 修法：按「主输入是不是触屏」判断**

```ts
const coarse = matchMedia("(pointer: coarse)").matches;
const narrow = matchMedia("(max-width: 720px)").matches;
const hasTouch = (navigator.maxTouchPoints ?? 0) > 0;
return coarse || (narrow && hasTouch);
```

| 设备 | coarse | narrow | hasTouch | 结果 |
|---|---|---|---|---|
| 手机 / 平板 | ✓ | — | ✓ | 触屏 UI ✓ |
| **桌面（含 Windows Chrome）** | ✗ | ✗ | ✗ | **桌面 UI + MSAA ✓** |
| 带触屏的笔记本 | ✗（主指针是鼠标） | ✗ | ✓ | 桌面 UI ✓ 正确 |
| 桌面端把窗口拉窄 | ✗ | ✓ | ✗ | 桌面 UI ✓ 正确 |

**(5) 验证**

无头 Chrome 里 `ontouchstart属性存在: false`、`maxTouchPoints: 0`
⇒ **这个环境复现不出用户的那条路径** ✓ 所以只能靠判据本身的推理来验证，
不能靠截图 —— 这一点如实说明。

| 判据 | 结果 |
|---|---|
| `tsc --noEmit` / `npm run build` | exit 0 / ✓ built ✓ |
| 桌面端 `isTouchDevice()` | `coarse=false, narrow=false, hasTouch=false` **⇒ false** ✓ |
| `touchUI.setVisible(false)`（main.ts L343） | ✓ 按键不再出现 |
| `antialias: !mobile` | ⇒ **true**，MSAA 恢复 ✓ |
| `setPixelRatio` | ⇒ 上限回到 **2** ✓ |

> **这个 bug 值得单独记一笔**：一个错误的判据同时造成了
> 「不该出现的 UI 出现了」和「该有的画质没有了」两个后果 ——
> 而后者一直没人报，因为它表现为"**看起来有点粗略**"，
> 很容易被归到美术资源上，而不是归到一行设备检测上。
