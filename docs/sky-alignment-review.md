# 音遇 · 与《光遇》对齐的美术/技术审查

- **审查对象**：`client/src/` 的角色模型、着色管线、特效、场景资产、手感物理
- **对照基准**：《Sky: Children of the Light》的角色语言与画面基调
- **审查方式**：源码精读 + `three@0.186.0` 源码级行为核对 + 离线数值复算（复现脚本见文末）
- **未做**：未启动浏览器做像素级截图对照（本文结论均为**代码级**，不是**截图级**）
- **标签**：`【观测】` 直接来自源码或等价复算 / `【推断】` 由观测推导 / `【第三方】` 来自并行审查 agent，我未逐条复算

## 0. 结论

**架构方向是对的，问题是三处"尺度错误" + 一处"体系缺失"。**

现在这套代码已经写了很多光遇该有的东西——真 Verlet 布料、真加速度物理、弹簧姿态通道、squash & stretch、toon ramp、体积光后处理、昼夜关键帧。差距不在"缺功能"，而在：

1. **角色模型混装了四种互不相容的美术语言**，其中 `elaina.glb` 材质结构决定了它**完全不受场景光照**；
2. **披风布料有三处量纲/量尺错误**，使它物理上不可能像光遇那样飘；
3. **整套发光体系整体失效**——所有粒子/特效的亮度都只有 bloom 阈值的一半，世界上几乎没有任何东西真的在发光；
4. **设计期的一次性缺失**：全场景没有 MSAA、云海被自家海面 100% 埋掉、地形是一个球冠。

按"改动成本 ÷ 观感提升"排序的优先级：

| 级别 | 条目 | 位置 | 一句话 |
|---|---|---|---|
| **P0** | `elaina.glb` 颜色全走 emissive | `avatar.ts:237-361` + GLB | baseColor 纯黑 + emissiveTexture → **永久不受光，白天深夜一个样，且全身过曝泛光** |

## 1. 角色模型：最核心的差距

### 1.1【P0】四种美术语言混装

**现状**【观测】：`AvatarModel` 有 9 个取值（`avatar.ts:22`），实现上是三套完全不同的管线：

| 模型 | 来源 | 三角面 | mesh 数 | 材质语言 |
|---|---|---|---|---|
| `classic` | 程序化拼装 | ~3k | ~25 个对象 | MeshToonMaterial + 32 档 ramp |
| `hooded` | `rogue-hooded.glb` | 6,035 | 12 | MeshStandardMaterial（PBR） |
| `elaina` | `elaina.glb` | **300,296** | **125** | baseColor 黑 + **纯 emissive** |
| `minion`/`corgi`/`duck`/`platypus`/`seal`/`owl` | 各 GLB | 240~508 | 1 | 低多边形卡通贴图 |

也就是：**一个渲染成手绘 toon 的圆润小人、一个 30 万面带描边的日式动画少女、一个 6千面写实兜帽旅人、一只低模柯基**，会同屏出现在同一个 64 人房间里。

**为什么离光遇有差距**：光遇最强烈的身份特征就是**视觉语言的绝对统一**——所有角色共用同一套造型语法（大圆头、面具脸、斗篷、极简四肢）、同一套着色（无描边、柔和明暗、无贴图细节）。混装会直接摧毁这个识别度；而 `elaina` 自带的 `_Line` 描边网格（详见下条）恰恰是**与光遇相反的**动画风格。

**改法**：
- 短期：把 `elaina` / `hooded` 收进"特殊外观"并接受风格断层，或直接下架。
- 中期：为所有 GLB 加一层**风格统一后处理**——加载后遍历材质，转成 `MeshToonMaterial` 或注入同样的 ramp，删掉 `*_Line` 描边网格，统一做 15% 降饱和。
- 长期：动物模型重做同一套比例语法（大眼、圆身、短肢）。低模 508 面本身不是问题，光遇角色也是几千面——问题在**造型语言不同**。

### 1.2【P0】`elaina.glb` 的材质结构：完全不受光照

**现状**【观测 · 我用 GLB 二进制解析 + three 源码核对】：

```json
{ "name": "body",
  "pbrMetallicRoughness": { "baseColorFactor": [0,0,0,1], "metallicFactor": 0 },
  "emissiveFactor": [1,1,1],
  "emissiveTexture": { "index": 1 },
  "extensions": { "KHR_materials_specular": { "specularFactor": 0 } } }
```

- 10 个材质**全部** `baseColorFactor = 纯黑`，其中 6 个把主贴图接在了 **emissiveTexture** 上，`emissiveFactor = 1,1,1`。
- 首个材质还带 `KHR_materials_emissive_strength: 1.5`。
- `*_Line` 系列（4 个）是**外向膨胀的描边壳**，无贴图、`emissiveFactor≈0.23`（暗色实体），`doubleSided=false`。
- 908 根骨骼、1314 个动画通道、12.58s 循环。

**为什么离光遇有差距**（这是本次审查单条影响最大的问题）：

1. **emissive 通道不参与光照计算**。黄昏的暖光、夜晚的冷蓝打上去**完全没反应**——角色永远是同一亮度同一颜色。光遇角色是深深融进环境光色的，这一条直接否定了"属于这个世界"。
2. **全身过曝**。emissive 强度 1.5 且贴图本身多为浅色，线性亮度普遍 >0.8 → 超过 bloom 阈值 → **整个角色都在泛光**，会糊成一团。作者自己在 `avatar.ts:107-108` 的注释里已经记录过同类现象（浅色气泡被泛光点亮）。
3. **描边与光遇语言相反**，且暗色实体壳会额外界定轮廓。
4. **908 骨 / 1314 通道**逐帧混合；`remote.ts:53` 对每个玩家都 `SkeletonUtils.clone` 一份；300k 面 / 125 mesh 意味着**单个角色 125 次 draw call**。在 `maxClients=64` 的房间里，只要有几个 `elaina`，draw call 会瞬间上万。

**改法**（三选一，按彻底程度）：
- **最小**：加载后把 `emissive` 归零、`baseColorFactor` 设为 `1,1,1`、把 `emissiveTexture` 挪到 `map`，并删掉所有名字含 `_Line` 的 mesh。这会把角色拉回"受光"的世界，但仍是日式动画风格。
- **中等**：再做一次减面 + 材质合并（125 → 4~6 个 mesh，300k → 30~50k 面），骨骼重定向到 ~80 骨。
- **推荐**：不作为可玩外观，仅保留为特殊 NPC 或参展彩蛋。

### 1.3【P0】程序化角色的几何：分段过低，剪影是多边形

**现状**【观测，`avatar.ts:376-548`】：

| 部件 | 几何 | 圆周分段 |
|---|---|---|
| 大腿 / 小腿 / 大臂 / 小臂 | `CapsuleGeometry(..., 4, 8)` | **8** |
| 脚 / 手 | `SphereGeometry(0.086, 8, 6)` | **8 × 6** |
| 躯干 | `SphereGeometry(1, 16, 14)` 拉成椭球 | 16 × 14 |
| 脸 | `SphereGeometry(0.32, 18, 16)` | 18 × 16 |
| 兜帽 | `SphereGeometry(0.345, 16, 12, 0, 2π, 0, 0.62π)` | 16 |
| 披风 | `PlaneGeometry(0.82, 0.9, 12, 16)` | 13 × 17 质点 |

**为什么离光遇有差距**：8 段的圆柱，其**剪影就是八边形**。toon ramp 会把明暗断层压平（这正是 toon 的优势），但**轮廓线藏不住**——手臂和腿的外缘会出现肉眼可见的折角。光遇角色的曲面是连续的，剪影上找不到任何直线段。

**改法**：四肢 `CapsuleGeometry(r, len, 6, 16)`、手脚 `SphereGeometry(r, 12, 10)`。总量增加很小（每个角色仍在 5k 面以内），但剪影质量是台阶式提升。**这是"一眼假"的最低成本修复。**

### 1.4【P1】轮廓光不统一，且不随光照方向变化

**现状**【观测，`avatar.ts:527-540`】：躯干和头各套一个放大的 `BackSide` 球壳（`MeshBasicMaterial` 纯色 #ffe4bb，opacity 0.22）当边缘光；**手臂、腿、披风、脚都没有**。

**为什么离光遇有差距**：
- 四肢轮廓是断的——躯干一圈亮、手臂没有，看起来像"上身包了个发光壳"。
- 壳是 `MeshBasicMaterial`，**不随光源方向变化**。光遇的轮廓光是**逆光时才强、顺光时几乎没有**。这里无论太阳在哪都在发光，是"探照灯式"的假边缘。
- GLB 模型走的是另一套（`patchRimMaterial` 的菲涅尔 rim，`avatar.ts:142-160`），两套并存。

**改法**：删掉 BackSide 壳，改用与 GLB 相同的菲涅尔 rim——但对**所有程序化材质**统一注入，并让它乘 `max(0, dot(sunDir, viewDir))` 之类的逆光系数，随 `lightState.sunDir` 每帧更新。这样四肢和躯干才连续，且光遇的"逆光轮廓"才成立。

### 1.5【P1】`toon.ts` 把随机噪声当 albedo

**现状**【观测，`toon.ts:17-52,84-89`】：用 256×256 的 canvas 生成"26 个径向色斑 + 逐像素白噪声"，`repeat(2,2)`，作为**所有 toon 材质的 `map`**（即漫反射 albedo）。

**为什么离光遇有差距**：
- 光遇的表面是**干净的纯色 + 大面积柔和渐变**，几乎没有纹理。逐像素噪声在 1.7m 高的角色上会让表面发"脏"，与"水彩晕染的干净"相反。
- 同一个纹理在地形上被拉到 75m/格、树干上 2.4m/格（`【第三方】`），**同一张笔触在 30 倍差异的尺度上重复**，两处都不好看。
- 贴图是 `Math.random()` 生成的，**每次刷新页面纹理都不同**（虽模块级缓存），画面不可复现。

**改法**：角色材质去掉 `map`（保留纯色 + ramp）；若确实要手绘感，改成**大尺度的低频色斑**（波长 ≥ 8 倍部件尺寸）而不是逐像素噪声，并为不同尺度提供不同 `repeat`；`anisotropy` 设为设备最大值。

### 1.6【P1】光照与阴影：没有 IBL，阴影图精度不够，且与接触阴影打架

**现状**【观测】：
- 光照只有 `HemisphereLight(0.82) + AmbientLight(0.36) + DirectionalLight(1.65)`，**全项目没有 `scene.environment`、没有 PMREM、没有 IBL**。
- 阴影图 2048、覆盖 ±62m → **6.05 cm/texel**。角色手臂直径 11.6cm ≈ **1.9 个 texel**。
- 角色同时 `castShadow + receiveShadow`（`avatar.ts:683-685`），**又有**一张接触阴影贴片（`avatar.ts:517-522`）。

**为什么离光遇有差距**：
- 无 IBL 时 `MeshStandardMaterial`（所有 GLB）**没有任何环境反射**，在暖色平光下会显得干、塑料。
- 6cm/texel 的阴影图里，手臂只有 2 个纹素宽 → 自阴影会出现块状/闪烁；而光遇角色基本**不投实时硬阴影**，用的是柔和的接触暗部。
- 现在是"硬方向光阴影 + 脚下软暗斑"两张叠加，方向相反时会露出两个影子。

**改法**：
- 加一张极低分辨率的环境贴图（用 `PMREMGenerator.fromScene()` 把天空球烘一次，昼夜各一张），给所有 PBR 材质提供环境色——这一步对玻璃、水、金属和角色的整体融合感提升明显。
- 角色改为 **`castShadow = false`，只保留接触阴影**（更接近光遇，也省一次阴影 pass）。若必须保留，把阴影相机收紧到跟随玩家 ±30m，纹素降到 1.8cm。
- 接触阴影的颜色目前硬编码 `#140e22`（`avatar.ts:183-185`），**不随昼夜变化**。白天亮草地上会显得脏，应随 `scene.fog.color` 走。

### 1.7【P2】眼睛、头顶烛光、光环

- **眼睛**（`avatar.ts:450-460`）：纯白 `MeshBasicMaterial`，**永远满亮**，不随昼夜。夜里会刺眼（且吃 bloom）。光遇的眼睛是发光体，应该有柔和的**光晕贴图**而不是硬边球。
- **头顶烛光 `wisp`**（`avatar.ts:543-548`）：一个纯色小球，**没有任何发光纹理或光晕**。光遇角色的头顶光点是有明显 bloom 光晕的。这是最容易改的"发光体"，加一张径向渐变 sprite 即可。
- **音乐光环**（`avatar.ts:560-588`）：`RingGeometry` + `AdditiveBlending`，是**几何环**（硬边）。光遇的距离光环是极柔的径向渐变。建议换贴图。

## 2. 披风布料：三处尺度错误（影响"像不像光遇"最大的一项）

架构方向是对的——真 Verlet、真约束松弛、真身体碰撞、真翼形混合。问题全在**量纲和量尺**上。

### 2.1【P0】力的时间尺度放大 60 倍 → 布料是硬帆布

**现状**【观测，`cape.ts:102,106`】：

```ts
const h = this.dt;                                        // = 1/60
this.pos[o+c] = p + (p - pr) * damping + windLocal.getComponent(c) * h * h * 60;
this.pos[v*3+1] -= gravity * h * h * 60;
```

标准 Verlet 的力项是 `a·h²`。因为 `h = 1/60` 固定，**`h·h·60 ≡ h`**，所以每步位移 = `a/60`，等价于有效加速度被放大到 **60 倍**。

取 `avatar.ts:503` 的 `gravity: 6` → 有效 **360 m/s²**。布料固有时间尺度 `T ∝ √(L/a)`，L≈0.9m 时 **T ≈ 0.31s**；再叠 `damping: 0.94`（60Hz 下速度半衰期仅 0.19s），结果是"抖一下就静止"。

**为什么离光遇有差距**：光遇披风落地回摆约 0.8~1.2s，是有重量、会荡的布。这里物理上就是一片**硬帆布/橡胶片**。注意这不产生"错值"（重力与风同乘，比值不变），它决定的是**时间尺度**。

**改法**：归一成规范式 `pos += vel·damping + a_total·h²`，重新标定起点：`gravity ≈ 28~36`（真 m/s² 语义）、`damping ≈ 0.985~0.99`、`iters 5 → 8`。

### 2.2【P0】锚距约束的量尺取了变形后的几何 → 1.45× 余量实际只剩 1.06×

**现状**【观测 + 我独立复算】：

```ts
// cape.ts:52  用「第 0 列变形后的竖直跨度」除以行数
this.rowLen = Math.abs(P(0).y - P((this.rows-1)*this.cols).y) / Math.max(1, this.rows-1);
// cape.ts:205
const maxLen = Math.floor(v / this.cols) * this.rowLen * 1.45;
```

`shapeCape`（见 2.3）已经把第 0 列整体上移过，所以量出来是**变形后的**跨度：

```
名义行距（PlaneGeometry(0.82,0.9,12,16)）= 0.05625
CapeSim 实际使用的 rowLen              = 0.04123   （打 73.3% 折）
→ maxLen(末行) = 16 × 0.04123 × 1.45 = 0.9565
→ 而 16 × 名义行距           =          0.9000
→ 设计意图 1.45× 余量，按名义行距折算实际只剩 1.063×
```

**为什么离光遇有差距**：作者想给的"1.45 倍拉伸余量"被吃掉 27%，布料几乎没有径向自由度 → 风没有余量把它吹开，观感是"被肩钉住的硬片"。

> **对第三方结论的更正**：并行审查报告称"静止时 39.9% 质点已被绑定"。我用等值复算（脚本见文末）**未能复现**该数字——构造期实际为 **11/208 = 5.3%**，最大 `d/maxLen = 4.31×`，且这 11 个全部是 `shapeCape` 把第 1 行抬到顶行之上造成的畸形（见 2.3）。但**量尺退化本身成立**（73.3%），结论方向不变，量级应按我这份数字。

**改法**：构造期按列累计 rest 链长（结构约束里已有 `rest`，直接复用），`maxLen = colLen[j] * ALLOW`，`ALLOW` 取 1.25~1.4；删掉 `rowLen`；把硬投影改成软约束（乘 0.5~0.8）。

### 2.3【P0】`shapeCape` 让第 1 行穿到顶行之上

**现状**【观测 + 我独立复算，`avatar.ts:488-498`】：

```ts
for (let i = 0; i < pos.count; i++) {
  if (pos.getY(i) > -0.01) continue;        // 只跳过顶行
  const x = pos.getX(i);
  const k = (x / 0.41 + 0.5);               // ← 注释写"0~1"，实际 x∈[-0.41,0.41] ⇒ k∈[-0.5,1.5]
  pos.setY(i, pos.getY(i) + jag * (0.22*|sin(k*π*2.7+0.4)| + 0.1*sin(k*9.1)));
  pos.setX(i, x * 0.86);
}
```

位移量只依赖 `x`，所以**每一列整体上移**；行 0 钉在 y=0，行 1 变成 `-0.05625 + c(x)`，`c(x)` 最大 0.24 时行 1 就跑到了顶行之上。

**我的复算结果**：

```
第 1 行高于第 0 行的列数 = 11 / 13      最大上抬 = 0.2571 m
row0 → row1 的竖直 rest 链长：最小 0.0283   最大 0.2579   （名义应为 0.05625）
```

**为什么离光遇有差距**：顶部一圈三角面翻面，`computeVertexNormals()` 把翻面法线平均进去 → 肩部一圈的 toon 明暗异常（双面材质能渲染，所以表现为"暗带/脏边"而不是消失）。同时这 0.2579m 的畸形首链正是 2.2 里唯一"看起来还救得回来"的地方。

**改法**：`k = x / 0.82 + 0.5`；且**只动底部 1~2 行**，或按 `t = (i/(rows-1))²` 沿列渐进变形，保证每列 rest 链长 ≈ 名义行距。

### 2.4【P0】缺惯性伪力 → 起步不甩、急停不前甩

**现状**【观测，`cape.ts:96-107` + `avatar.ts:981-987`】：所有质点位置都表达在 `group` 坐标系里（`avatar.ts:506` 注释明确说明），而 `group` 只承载 `rotation.y`——**角色的世界位移完全不进入这个坐标系**。进入布料的唯一外因 `windLocal` 是速度的 0.55 倍（气动阻力），**不是加速度**。

**为什么离光遇有差距**：这是"起步甩、急停前甩"在结构上不存在的原因。急停时 `velocity→0` → 风→0 → 布只是被 damping 拉回原位，**永远不会向前甩过头**。`cape.ts:9` 的注释"角色加速→布因惯性滞后甩动"在实现上不成立。

**改法**：主循环给出平滑加速度向量（本地差分 + 低通，限幅 ±14 m/s²），在 `animate()` 里用同一个 yaw 逆变换转到局部，`windWorld.addScaledVector(accelLocal, -K)`，K ≈ 0.8~1.2。

### 2.5【P1】碰撞代理比渲染网格胖 13~19% → 静止时斗篷"悬在背后"

**现状**【观测】：`cape.ts:78-81` 的椭球 `T_X=0.357 / T_Y=0.412 / T_Z=0.312`，而渲染躯干是 `scale(0.315, 0.345, 0.275)`（`avatar.ts:403`）→ **静态间隙 3.7cm**。头球 `H_R=0.376` vs 渲染头 z 半径 0.344 → 3.2cm。

**为什么离光遇有差距**：光遇披风静止时是**贴着后背**的（能看到布料轮廓压在背上）。这里不管有没有风，都被顶在 3.7cm 外，观感是"一块板悬在背后"。

**改法**：代理改为 `渲染尺寸 + 0.005~0.01`，并加一条弱向心吸引力（权重 <0.15）——贴背但风一来能被吹开。

### 2.6【P0】内层披风整片落在躯干内部 → 双层实际只有一层

**现状**【观测，`avatar.ts:510-525`】：`innerCape.position.set(0, 0.98, -0.12)`，内层世界 z ≈ −0.12 ~ −0.179。而躯干椭球在 y=0.70 处背面 z = −0.263、y=0.90 处 −0.136。**y≈0.56~0.90 整段落在不透明躯干内部**，被完全遮住。

**改法**：把外层椭球余量收到 0.01 后，内层放到 z=−0.20 并跟随外层做 0.5 倍位移；或让内层也走布料。

### 2.7【P1】前界硬平面吃掉了几乎全部前向自由度

**现状**【观测，`cape.ts:87,182-185`】：直立时 `frontBase = -0.06`，而肩锚点在 z=−0.17~−0.22、躯干背面在 z=−0.312。上身段布料被夹在 **0.25m 的薄壳**里，前向摆幅上限约 17°。

**改法**：把前界从"全局 z 平面"改成**身体区域平面**（仅对 `y∈[0.28,1.05]` 生效 + 软系数）；或者撤掉它，改为直接压掉 `avatar.ts:984` 的上掀风系数——上掀才是真问题，前界只是压制症状。

### 2.8【P2】其它

- **无自碰撞**（全文件只有距离约束，无质点-质点排斥）。
- **无质量差异 / 无空间湍流**（湍流只有时间正弦，无空间噪声）。
- **地面钳制只钳 y，不动 `prev`、不加摩擦**（`cape.ts:186`）→ 落地布料会"弹"，且**不可能堆叠**——注释里"坐下时披风自然堆叠在地面"用这个实现做不到。

## 3. 步态与手感

### 3.1【P0】摆腿幅度写死 → 与速度无关的恒定 ~58% 脚滑

**现状**【观测，`avatar.ts:714-718, 876-898`】：步频与速度**联动是正确的**（`stepRate = π·speed/strideLen`），但摆腿幅度是常数：

```ts
const strideLen = 0.34 + 0.5 * speedN;
const stepRate  = clamp((Math.PI * speed) / strideLen, 3.0, 24);
legL.root.rotation.x = strideL * 0.55 * walkAmp - ...      // 0.55 rad 常数
```

腿长由几何决定：髋 y=0.46、膝 −0.19、脚 −0.15 → **L ≈ 0.34m**。

**推算**【推断】：走（3.6m/s）时脚相对身体每步行程 `2·0.34·sin(0.371) ≈ 0.25m`，而身体前进 0.59m → **滑 0.34m（58%）**；跑（7.2m/s）时 0.35m vs 0.84m → **滑 0.49m（58%）**。另外 `stepRate` 上限 24 在满速下已触发（理想值 26.9），再叠 ~10% 频率不足。

**为什么离光遇有差距**：脚滑是"不像光遇"的第一观感来源——光遇的脚步是踩实的。

**改法**：让幅度与步幅联动，`swingAmp = asin(min(0.95, strideLen / (2·0.34)))`（即 `2·L·sinθ = strideLen`），并把 `stepRate` 上限放到 32。彻底解法是两段 IK 落脚，但比例修正能消除大部分问题。

### 3.2【P1】滑翔接管是一帧硬切，且每帧用 yaw 重建速度

**现状**【观测，`physics.ts:214-232`】：

```ts
if (glidingNow) this.glideSpeed = Math.max(4, this.horizSpeed);
this.vel.y = this.glideSpeed * sinP + updraftAt(...) * 0.85;
const hs = this.glideSpeed * cosP;
this.vel.x = Math.sin(this.yaw) * hs;      // ← 每帧覆盖
this.vel.z = Math.cos(this.yaw) * hs;
```

**推算**【推断】：助跑起跳 7.2m/s 时接管瞬间 `vel.y` 从 +1.2 变 −1.0 → **单帧 Δvy ≈ −2.2 m/s**，轨迹上有明显拐点。站立起跳时水平速度**一帧内 0 → 3.96 m/s**，角色凭空平移。且 `vel.x/z` 每帧被 yaw 重建 → `resolveColliders`（`physics.ts:301`）刚切掉的法向速度下一帧被覆盖 → **贴树/贴石飞行持续"推进-弹出"抖动**，撞击也不会掉速。

**改法**：接管用 0.25~0.4s 混合 `vel.y`；`glideSpeed` 同理不要瞬跳；滑翔改为"速度积分 + 沿航向推力/阻力"（`vel += (forward·accel − vel·drag)·dt`），yaw 只负责转向。

### 3.3【P1】相机稳态滞后 1.24m，且只有地形地板钳制

**现状**【观测，`controls.ts:49,362-373`】：`camSpring = SpringV3(110, 19)` → ω=10.49、ζ=0.906。二阶系统跟踪匀速输入的稳态误差 = `2ζv/ω`：7.2m/s → **1.24m**。而 `lookAt` 又被 `+0.16·vel`（=1.15m）推回角色身上，两者几乎抵消，所以**静止看是对的**——但急转/急停时焦点要追 1.24m×2 的偏移，角色会在屏幕上大幅横甩。

相机垂直方向只有 `max(cy, terrainHeight + 0.8)` 硬钳制，**没有遮挡处理**，且钳制不经过弹簧 → 上坡/贴山时镜头 y 瞬跳。

**改法**：给焦点加**速度前馈** `target = focusRaw + vel·0.10`，稳态误差即归零；对 `camGround` 也走一个弹簧；再从焦点到相机做 8~12 点地形采样，命中就把 `camDist` 收近（岛是解析高度场，非常便宜）。

### 3.4【P1】触屏也请求 Pointer Lock；摇杆奔跑阈值造成 3.2m/s 阶跃

- `controls.ts:127-137` 的 `pointerdown` **没有判断 `e.pointerType`**。Android Chrome 支持触摸触发 pointer lock，一旦锁定，转视角走 `movementX` 分支，而触摸的 `movementX` 通常无意义 → **移动端拖屏转视角直接失效**。改：加 `e.pointerType === "mouse"`。
- `touch.ts:75-86` 摇杆线性映射，无死区（`joyLen > 0.08` ≈ 3.4px）→ 手指微抖就转向。`> 0.88` 走奔跑：`0.875 → 3.15m/s` vs `0.885 → 6.37m/s`，**1% 行程内速度目标跳 +3.2 m/s**（`groundAccel=16` 会在 0.2s 内追到）→ 走→跑是硬开关。改：加 0.14 死区 + `pow(t, 1.25)` 的 expo，奔跑改成 `smoothstep(0.75, 1.0, len)` 连续插值。
- `touch.ts:33-47` 飞行按钮没有 `setPointerCapture`，手指轻滑出按钮边界触发 `pointerleave` → **滑翔立即中断**。

### 3.5【P1】`remote.ts:219` 的 `air` 判据错误

```ts
const air = target.mov === 3 || mov === 4 ? 2
          : g.position.y - terrainHeight(x, z) > 0.6 ? 1 : 0;
```

`terrainHeight` 是**地形高度场**，不含岩石顶/灯塔环廊/木凳，也不含水下修正。于是：

- **站在岩石/长凳/秋千上**：`y − terrain > 0.6` → 判成腾空 → **站着的人做出双臂上摆、腿收起的下落姿势**。
- **深水里游泳**：水面 −0.28 而海床 ≈ −1.6 → `y − terrain ≈ 2.7` → 判成腾空，同时 `swim: true` 也在驱动 → **半游半坠**。

而**信息其实已在协议里**：`mov === 5` 就是"普通腾空"（`controls.ts:334`）。

**改法**（一行）：`const air = mov === 3 || mov === 4 ? 2 : mov === 5 ? 1 : 0;`

### 3.6【P2】落地无回弹、起跳无预备

`squash`/`stretch` 都在（`avatar.ts:739-742`），但都是**单调线性衰减**（`squash` 4/s、`stretch` 3.2/s），没有过冲回弹；`stretch` 在离地那一帧才赋值 → 是**离地后的伸展**，不是"蹲下蓄力"。改：`squash` 换成 `Spring(180, 12)`（ζ≈0.45，欠阻尼自动产生回弹）；起跳前 0.08~0.12s 给一个负 `squash` 蓄力——`motion.ts` 的 `Spring` 现成可用。

### 3.7【P2】弹簧是帧率相关的

`motion.ts:29,56`：`h = Math.min(dt, 1/30)`。`dt > 1/30` 时弹簧按更小时间推进 → **掉到 20fps 时收敛速度只剩 2/3**。相机和身体姿态都吃这个。改：用闭式解，或固定步长子步（累加器按 1/120 步进）。另外各处弹簧全是手写 `(k, c)`，阻尼比从 0.45 到 0.97 不等，建议构造时改传 `(ω, ζ)`。

### 3.8【P2】握手跟随稳态误差 1.2m

`main.ts:1267-1273`：`k = min(1, dt*6)` 的一阶指数追随，匀速 7.2m/s 时稳态误差 = `v/6 = 1.2m` → 牵手两人间距从 0.78m 被拉到近 2m，光带被拉长、手对不上。改：加队长速度前馈 `followTarget += leadVel·0.17`。

## 4. 发光体系：整体失效

### 4.1【P0】阈值链条已确证

**现状**【观测，three 源码级】：

1. `EffectComposer.js:69` 的 RT 是 `HalfFloatType` → 中间缓冲是**线性 HDR、未 tone-map**。
2. `WebGLPrograms` 渲染到 RT 时 `toneMapping = NoToneMapping`。
3. `LuminosityHighPassShader`：`alpha = smoothstep(threshold, threshold + smoothWidth, luminance)`，而 `UnrealBloomPass.js:137` 把 `smoothWidth` 硬编码成 **0.01**。
4. `scene.ts:239-242` 传入 `threshold = 0.8`。

→ **任何片元必须在最终线性缓冲里让 Rec709 luma > 0.8 才会产生辉光**，且 0.79→0.81 几乎是硬切。

### 4.2 逐模块核算：全部只有阈值的一半

【观测 + 计算】

| 模块 | 线性色 × 透明度 | 峰值 luma | 阈值 | 结果 |
|---|---|---|---|---|
| motes 光尘 `#ffe9b8`（`particles.ts:103`+`scene.ts:388`） | (1.000, 0.815, 0.479) × 0.5 | **0.415** | 0.8 | ❌ 永不发光 |
| fireflies `#e5ffb0`（`uOpacity` 卡在 0.6） | (0.784, 1.000, 0.434) × 0.6 | **0.548** | 0.8 | ❌ |
| embers 余烬 `#ffc07a` × 0.9 | (1.000, 0.527, 0.195) × 0.9 | **0.543** | 0.8 | ❌ + 还是**实心方块** |
| bursts 扑翼 `#ff9ecf` × 0.9 | (1.000, 0.342, 0.624) × 0.9 | **0.452** | 0.8 | ❌ |
| windlines 风线 | — | ~0.3 | 0.8 | ❌ |
| musicfx 节拍涟漪 | — | ~0.25~0.35 | 0.8 | ❌ |
| beacons 光柱 | — | ~0.2~0.3 | 0.8 | ❌ **模块功能完全没实现** |
| voicefx 语音环 | — | ~0.3~0.55 | 0.8 | ❌ |
| musicfx 音符字形（唯一例外） | (1.000, 1.000, 1.000) × 0.98 | **0.980** | 0.8 | ✅ 真的在发光 |

（上表 luma 用 Rec709 权重按 sRGB→线性换算，已复算，脚本 `%TEMP%\luma.mjs`。）

**同一个 codebase 里只有一个元素在发光**——这反证了阈值理论：不是美术选择，是**接口用错**。

两个关键推论：
- pass 顺序是 `godray → bloom → OutputPass`，即 `toneMappingExposure` **作用在 bloom 之后** → **提高曝光永远调不出粒子发光**，这是最容易走进的死胡同。
- godray 在 bloom 之前把 `ray × uIntensity × 2.2` 加进缓冲，会先把太阳/亮空附近的背景推过阈值 → 造成"粒子只在白天亮天空前看起来在发光、夜里完全不亮"的错觉，**恰好与光遇（暗处才是光的主场）相反**。

**统一改法**（一条规则贯穿全项目）：
- ShaderMaterial：`gl_FragColor = vec4(uColor * uEmissive, a * uOpacity * vTw);`，`uEmissive` 取 2.0~2.6。
- 内置材质：`material.color.copy(c).multiplyScalar(2.4)`（`Color` 是 float 不 clamp，>1 的值能无损进 HalfFloat，由 OutputPass 的 ACES 滚降）。
- twinkle 设计在阈值**之上**波动（1.2→2.6），而不是穿过 0.8——否则 sin 闪烁每周期会有一次"突然点亮/熄灭"的时间域走样。

### 4.3【P1】三个"接口用错"的具体 bug

1. **`scene.ts:387` 是 no-op**：`fireflies.points.material` 是 `ShaderMaterial`（`particles.ts:67`），而 `scene.ts:328` 把它断言成 `PointsMaterial` 后写 `.opacity`。three 0.186 的 `WebGLMaterials.js:130-133` 中 `isShaderMaterial` 分支**只设 `uniformsNeedUpdate = false`，不写 opacity**（`uniforms.opacity.value = material.opacity` 在 128 行的 `isShadowMaterial` 分支）。→ **萤火虫的 `uOpacity` 永远停在构造值 0.6，正午也在满亮度发荧光绿**，注释里"白天几乎看不见"完全没生效。同一段里 motes 写的是 `uniforms.uOpacity.value`（正确）——这个不对称就是证据。

2. **余烬是实心方块**：`particles.ts:159-167` 的 `PointsMaterial` **没有 `map`**。three 的 `points.glsl.js` 片元走 `map_particle_fragment`，而那里**只在 `#ifdef USE_MAP` 时才采样 `gl_PointCoord`** → **没有贴图的点就是实心方块**。`sizeAttenuation` 用 `scale = drawingBufferHeight·0.5`，1080p@DPR2（backing 2160）时 3 米处约 **76 设备像素的实心暖色方块**。这是全套里最"一眼假"的一处。

3. **motes 尺寸硬编码**：`particles.ts:92` 的 `gl_PointSize = uSize * (140.0 / -mv.z)`。140 ≈ `height·0.5`（height=280），即**假设画布只有 280px 高** → 在高分屏上粒子相对画面小得多；且与 FOV 无关，而 `controls.ts:375` 会在滑翔时加 FOV → 飞行时粒子尺度跳变。改：每帧写 `uSizeScale = drawingBufferHeight·0.5 / (2·tan(fov/2))`，并 `clamp(1, 64)`（很多驱动 point size 上限 63.9）。

### 4.4【P1】萤火虫/光尘的动态是"整片集体呼吸"

`particles.ts:87-90`：240 颗粒共用 3 个频率（0.3/0.2/0.26），只有相位差 → 视觉上是**一坨整体在摆动**。且 `vTw = 0.55 + 0.45·sin(...)` 最低只到 0.1，**永不归零** → 光尘不会真正"生灭"。

改：频率按属性随机化（`0.12 + rand·0.35`）并叠低频层；`vTw = pow(0.5+0.5·sin(...), 2.0)`；加每颗 8~20s 的慢包络，低于 0.02 时 `discard`。再加 `aSizeRand`/`aTint` 做逐颗尺寸与色相差异（现在是全片唯一 uniform，240 颗完全相同）。

### 4.5【P1】`lightstate.ts` 只有"全局调暗"，没有"暗处提亮"

7 个特效模块里**一个都没有 import `lightState`**。`scene.ts:388` 是唯一的消费点，而且做的是**减法**（夜里把光尘压到 0.075）。

但光遇的物理与感知都是：**环境越暗，光点越显眼**。当前架构只做减法，没有任何模块做"暗处提亮"。

**改法**：把自发光系数统一由 `lightState.night` 驱动（`uEmissive = 2.0 + night·1.4`），并在 `lightstate.ts` 加一个共用的 `fxGain()` 供所有 FX 模块使用，让"夜晚 = 发光物主场"成为**架构级不变量**，而不是 6 处各自拍脑袋的常数。

### 4.6【P2】内存泄漏与池抢占

- `voicefx.ts:83-87`：发射器销毁时只从 Map 删除，**group 里的 4 个 Mesh + 4 个 Material 永久留下**。一局轮换 100 个说话者 = 400 个对象泄漏 → 是"跑一小时后掉帧"的典型来源。
- `beacons.ts` 的 pool 只增不减 → 每个来过的 key 永久留 1 Group + 2 Mesh + 2 Material + 1 Geometry。
- `bursts.ts:64` 的 `pool.find(...) ?? pool.find(p => p.kind === kind)` 第二条 fallback 会**复用正在播放的爆发**，把别人看得见的特效瞬移走。
- `musicfx.ts:177` `baseX.get(n)!` 每帧每音符一次 Map 查表；`musicfx.ts:110` 每次生成音符 `new THREE.Color(...)`（全套唯一的每帧级分配）。

## 5. 场景资产

### 5.1【P0】全场景没有 MSAA（一行可修）

**现状**【观测，three 源码级】：`scene.ts:47` 建 renderer 时传了 `antialias: !mobile`，但 `scene.ts:233` 的 `EffectComposer` 把场景渲染到自己的 offscreen RT 上，而 `EffectComposer.js:69` 只传了 `{ type: HalfFloatType }`——**全文 `samples` 出现 0 次** → `samples = 0`。

`antialias` 只作用于默认帧缓冲，所以**MSAA 完全没有生效**。海岸线、草叶边缘、灯塔、星星、地形剪影全是硬阶梯。

**改法**（`scene.ts:233` 之后）：
```ts
composer.renderTarget1.samples = 4;
composer.renderTarget2.samples = 4;   // 移动端按 isTouchDevice() 降到 2
```

### 5.2【P0】云海 100% 被自家海面埋掉

**现状**【观测，`clouds.ts:81-90` vs `water.ts:19-20,46-48`】：26 朵低云在 **y = −8 ~ −3.5**（`clouds.ts:83`），而海面是一张 **y = 0.55、半径 0~500 的不透明平面**（`water.ts:19-20` 的 `NEAR_WATER_RADIUS=120 / OCEAN_RADIUS=500`，`transparent: false, depthWrite: true`）。

相机在水面之上时，视线到云的路程**必然穿过海面** → 深度测试全部丢弃。26 朵 × 平均 8 个 puff = **208/272 个 sprite（76%）彻底不可见**。"岛漂浮在云海上"目前是"岛泡在一个不透明的湖里"。

**改法**（美术方向级决策）：
- **推荐**：取消远海。把云海当地面——删掉 `OCEAN_RADIUS=500` 的环，水面只保留到 r≈130~150 的潟湖，r>150 全交给云海，再加一层薄雾幕作底座。
- **最小**：保留海面，把云海抬到 y = +1.5~+5。
- 无论哪种，云海材质都要单独的雾衰减（当前 `fog: true`，r=268 处雾权重 78%，远侧云海会被抹平）。

### 5.3【P0】云是 272 个独立 Sprite + 272 个克隆材质，零受光

**现状**【观测，`clouds.ts:41,58-62`】：每个 puff **克隆一份材质、单独一个 Sprite**。`SpriteMaterial` **不受光照** → 整朵云恒定颜色，**没有顶亮底暗、没有受光/背光面、没有边缘厚度**；贴图本身只是径向 alpha 渐变，没有任何明暗信息。所以"蓬松体积感云团"在这套结构下**做不出来**。

性能上：272 次 draw call，占全场景约 410 次的 **66%**；透明排序每帧还要遍历 272 个对象。

**改法**（1 个 draw call + 假体积，关键在**用 UV 反推半球法线**）：
```glsl
vec2 q = vUv * 2.0 - 1.0;
float r2 = min(1.0, dot(q, q));
vec3 n = vec3(q, sqrt(1.0 - r2));                 // 半球法线 = impostor 体积感的关键
float lam = dot(n, uSunDir) * 0.5 + 0.5;
vec3 col = mix(uCloudShadow, uCloudLit, pow(lam, 1.2));
col += uRimColor * pow(1.0 - max(dot(n, V), 0.0), 3.0) * 0.35;   // 边缘厚度
float a = smoothstep(1.0, 0.35, r2) * uOpacity;
```
再用一个 `InstancedMesh`（顶点着色器做 billboard）承载全部 puff；团块排布改成"平底花椰菜"（顶部 3~4 个大 puff、底部 4~6 个小 puff，整体向太阳侧偏移 12%）。

**另外云的运动有两个 bug**：`clouds.ts:121` 的 `c.angle += c.speed * 0.016` **硬编码 60fps**（144Hz 上快 2.4 倍）；`clouds.ts:124` 的 `position.y +=` 是**逐帧积分**（帧率波动会留下永久偏移，应改绝对赋值）。且所有云绕**原点**公转 → 视觉上是"云海围绕你旋转"。光遇的云海相对岛屿近乎静止。

### 5.4【P0】地形是单一球冠，三色区实际只有两色

**现状**【观测】：

```ts
let h = 5.5 * Math.pow(Math.max(0, 1 - rr), 1.25) + 1.2;      // heightfield.ts:35
h += 9.5 * Math.exp(-(dxh*dxh + dzh*dzh) / 320);              // :39 唯一特征：一个高斯山包
```

这是一条**处处二阶可导的凸穹顶**。实测（岛内水面以上 2486 个顶点）：

| 坡度 | 面积占比 |
|---|---|
| 0.00–0.20 | **50.1%** |
| 0.20–0.30 | 23.0% |
| 0.30–0.50 | 16.2% |
| ≥0.60 | 6.9%（**全部是贴水线的岸坡**） |

三色区实测（按 `terrain.ts:40-46` 等值复刻）：**沙 374 m² (6.2%) / 岩 254 m² (4.2%) / 草 5442 m² (89.7%)**。其中 `h > 11.5` 触发岩色的只有 **3 个顶点**（岛最高 11.575m）。

**为什么离光遇有差距**：光遇的地貌识别度 = **青灰崖 + 苦艾绿草 + 暖米沙**三色大面积并置，造型语言是"3~5 层台地 + 台地之间 2~4m 的圆润崖唇"。这里 89.7% 是同一个绿，纵向是连续幂函数，横向最大坡度 0.62（31°）——从任何角度看都是"一个馒头"。另外 `C_ROCK = #aca3cd` 是**薰衣草紫**（H≈253°），不是光遇的岩石青灰（H≈200~210°）。

**改法**：
```ts
// ① 台阶化：把高度向台面吸附，台面之间保留圆润崖唇
const TIERS = [1.8, 3.6, 6.2, 9.4];
h = terracing(h, 0.78);
// ② 打破径向对称：55m 波长的低频噪声，只在离广场 15m 外生效
h += 3.4 * (fbm2(x*0.018, z*0.018) - 0.5) * smoothstep(12, 30, r);
```
```ts
// ③ 三色阈值按实测坡度分布重设，岩带与台地崖唇绑定
const cliff = slope > 0.28 ? 1 : 0;        // 从 0.62 降到 0.28
const rockMix = clamp(max(cliff, tierRim(h, TIERS, 1.4)) * 0.9, 0, 1);
// C_ROCK → #93a2ab (H≈201°) 青灰；目标比例 草 60~70% / 岩 20~30% / 沙 8~12%
```
> **联动约束**：`water.ts:28-42` 把 `terrainHeight` 整段**重抄成了 GLSL**。任何对 `heightfield.ts` 的改动必须同步改这一段，否则岸线裁剪、水深、浅滩色带全部错位。建议把地形函数抽成单一 GLSL 字符串常量导出。

### 5.5【P1】地形没有 AO/曲率着色，"向阳坡染夕阳"等于常数

**现状**【观测，`terrain.ts:56-60`】：`nrm = (-nx, 1.6, -nz)`，`sunDir` 是**固定值** `(-0.62, 0.3, -0.42)`（不随 `scene.ts:357-368` 的实时日月轨道变化）。平地 `nrm·sun = 0.373` 恒定 → 因为 73% 的岛坡度 <0.2，这一项几乎处处输出同一个值 → **它没在表达坡向，只是在给全岛统一刷一层米色**。

而光遇地形"能看出形状"靠的是**台地顶面受光 / 崖壁背光 / 凹地自然荫蔽（AO）**，这里三者全无。

**改法**（地形是静态的，可一次性烘焙，成本几乎为零）：每顶点做 8 方向 × 3 步的最小水平角遮挡 → 乘进顶点色；再叠一层曲率暗角（`h` 低于局部均值 → 变暗）。97×97×8×3 ≈ 22.6 万次采样，构建期几十毫秒。**这是性价比最高的单点改动。**

### 5.6【P0】水面法线恒为竖直 → 水是纯色平板

**现状**【观测，`water.ts:75-91`】：三个波幅度 0.10/0.08/0.04，波长 `2π/0.11 = 57m`、`70m`、`35m`。最大梯度 `0.10·0.11 + 0.04·0.18 = 0.0182`；按 `e = 1.5` 差分 `hx ≤ 0.055` → 法线倾角 `atan(0.055/3.0) ≈ **1.5°**`。

后果链：`N≈(0,1,0)` → `fresnel = pow(1-dot(V,N),3)` 只由视角决定（全屏一个平滑渐变，**没有纹路**）→ `spec = pow(dot(R,uSunDir),18)` 是一个几乎不动的大光斑。所以"大面积低对比的水纹"（`water.ts:121` 注释）在数学上**根本无法出现**。

**改法**：**位移用大浪，法线用细节波**——加 4 倍频细节波（λ = 3.0/1.2/0.5/0.22m，amp = 0.022/0.010/0.005/0.002），差分尺度 `e` 从 1.5 降到 0.22 → 合梯度 ≈0.20 → 法线倾斜 **8~12°** → fresnel 与 `pow(spec,18)` 自然出现"波光走位"，不需要任何贴图。

**另一个问题（色彩空间）**【观测 + 计算】：`water.ts:117-119` 的 `vec3(0.35,0.80,0.72)` / `vec3(0.07,0.27,0.50)` 是 **GLSL 字面量，处在 linear 工作空间**，而 `new THREE.Color("#...")` 会做 sRGB→linear。所以作者心里的"深青蓝"实际等效 sRGB 是：

| GLSL 字面量 | 实际等效 sRGB | 观感 |
|---|---|---|
| `(0.35,0.80,0.72)` 浅水 | **#9FE7DC** | 苍白薄荷 |
| `(0.07,0.27,0.50)` 深水 | **#4B8EBB** | 中等钢蓝 |

改：全部改成通过 uniform 传入的 `THREE.Color("#...")`；并把深度项换成 Beer–Lambert `exp(-vec3(0.55,0.18,0.12)·depth)`，让远海自然走到深青蓝而不是被 `clamp(...,2.2m)` 一刀切平。同时把水底沙色解析地混进来（**不做真折射也能"看见水底"**），这是光遇浅滩通透感的关键。

### 5.7【P1】其它场景问题

- **沙滩只有 1.34m 宽**（最窄 0.30m / 最宽 5.36m / 均值 1.34m）。光遇的沙滩是 10~30m 的宽阔暖色带。根因是 `heightfield.ts:51` 用一个 `smoothstep` 直接从陆地落到 −1.6，没有"浅水台 + 沙滩 + 陡岸"的分级剖面。
- **场景极度空旷**：全岛 **9 棵树**（`props.ts:554` 的 `if (terrainHeight < 1.4) continue` 剔掉了 3 棵候选）+ 10 块石头里有 **6 块落在水下或岛外**（实测 `(-20,42) h=2.31` 可用，但 `(10,-48) h=-13.38`、`(20,-44) h=-23.04` 完全不可见）+ 草覆盖仅 **16.1%**（5250 片 / 6069 m² = 0.87 片/m²）。`heightfield.ts:68-71` 命名的"西花田""北林地"下面实际什么都没有。改：用泊松盘在干地上生成，树 45~70 棵/地标簇，石 30~60 组卵石簇，草提到 2500~3500 簇。
- **道具共 ~123 次 draw call**（9 棵树 = 54 次、灯塔 = 36 次），阴影 pass 再来一遍。改：每棵树木部 `mergeGeometries`，更彻底是**整棵树做 InstancedMesh**（摆动放顶点着色器）→ 1 次。
- **长凳没有腿且一侧悬空**：凳环 r=3.6 处 `slope=0.427`，凳面进深 0.55m → 内外高差 **0.24m**，一侧埋土一侧悬空 ~18cm。所有道具都应按地形法线对齐（`quaternion.setFromUnitVectors(UP, normal)`）并按**脚点**而非组心落位。
- **树冠色比地面草更亮且色相偏离**（`#bfe3ab` 是全场景最亮的绿），且**绕过了 toon.ts 的 15% 降饱和**——降饱和只作用于 `material.color`，而树冠用 `kit.mat("#ffffff", true)` + 顶点色 → **没走降饱和**。同理地形顶点色、草/水的 GLSL 常量、天空色板外的颜色都没走。所谓"色板统一"实际只覆盖一半材质。另外**树完全静止**（`updates` 里只有花/草/灯塔/篝火），光遇的树冠是持续微摆的。
- **星星是 5×5 像素的实心方块**：`sky.ts:87` 的 `floor(d*220)` → 每 cell 角尺寸 0.26°，1080p/55°FOV → 5px。改：cell 内抖动点 + `exp(-dist2*900)` 径向衰减 + `pow(hash,3)` 做星等分布。
- **`setDayPhase` 被每帧调用**（`main.ts:1527`）→ 每帧约 8 个堆对象 + 6 次 hex 字符串解析 + 272 次材质写入。改：提到模块级常量 + `lt(prev, cur)` 守卫（照抄 `props.ts:577` 已有的思路）。
- **草的雾是硬编码的**（`props.ts:237,259` 用 `#eecfa4` / 0.0042），而夜里场景雾是 `#2a3354` / 0.0055 → 60m 处草比地面**少 40% 的雾**，且雾目标色是亮的暖米 → **夜里草地会浮出一片片发亮的奶色斑块**。改：让 `scene.setDayPhase` 每帧写入草的 `uFogColor/uFogDensity`。

## 7. 最高性价比的改动（按批次）

### 第一批：半天内，改动小、收益立竿见影

1. **打开 MSAA**（`scene.ts:233` 后两行）——一行代码消掉"廉价感"的最大来源。
2. **修 `remote.ts:219` 的 `air` 判据**（一行）——消掉"站石头上的人做坠落动作""游泳的人半游半坠"两个最显眼的多人穿帮。
3. **修 `scene.ts:387` 的 no-op**（改断言的类型 + 写 `uniforms.uOpacity.value`）——萤火虫白天终于会灭。
4. **给所有发光体乘 HDR 自发光系数**（`uEmissive` 2.2 / `color.multiplyScalar(2.4)`）——**这一条单独就能把"没在发光"变成"真的在发光"，是全套光遇感的一半**。改动遍及 7 个 FX 模块，但每处 1~2 行。
5. **提高四肢几何分段**（`avatar.ts:376-433`）——剪影从八边形变回圆弧。

### 第二批：1~2 天，解决"最不像光遇"的三件事

6. **斗篷三处尺度错误一起修**（`cape.ts:52,102,106` + `avatar.ts:489-497,981-987`）——量纲归一、量尺换成逐列 rest 链长、`shapeCape` 只动底部、注入 `-a` 惯性伪力。**这是"像不像光遇"影响最大的一项**。
7. **步态幅度与步幅联动**（`avatar.ts:716-717,888-897`）——消除 58% 脚滑。
8. **`elaina.glb` 材质修正或下架**（`avatar.ts:237-361`）——把 emissive 挪回 baseColor、删 `_Line` mesh、降面合并材质。这一条同时解决"风格断层""不受光""过曝""125 draw call"四个问题。

### 第三批：3~5 天，画面基调

9. **云海重建**：脱离水面 + 1 个 InstancedMesh + 半球法线受光（`clouds.ts` 全文件 + `water.ts:20`）。**天空/地平线有没有光遇味，几乎全靠这一条**，同时砍掉 66% 的 draw call。
